# Native multi-sensor capture and retained RAW/ISP experiments

In Experiments, select **CARLA sensor capture**, load the supported rig, preview
the exact native capability/configuration and submit an immutable experiment.
The installed CARLA engine records two RGB cameras, one LiDAR and one radar at
10 Hz for 10–30 seconds. Frames are streamed to native files and retained in a
hash-checked archive. Image previews and native evidence are available in the
same workspace. The pose convention and rotation order are explicit; native
measurement coordinates are preserved instead of silently relabelled.

The first coherent world snapshot must match the requested map spawn. A stale
immediate post-spawn API transform is retained as a diagnostic. Every retained
measurement is checked against its world snapshot, actor/parent identity,
mount transform, frame and clock. Native blueprint parameters are read back.
The adapter refuses a changed codec/map/build, unsupported attributes, extra
actors, missing records, duplicate archive members, invalid file closure or
unconfirmed owned-actor cleanup. It does not reload maps or restart CARLA.

`same_scene_sensor_ab` fixes the scene definition and spawn, then captures two
explicit rigs. It is a **sequential** comparison: world clock, traffic lights
and renderer history are not frozen. It cannot establish a controlled detector
accuracy difference. Native RGB is postprocessed engine RGB; physical RAW,
calibrated radar/LiDAR response, depth and segmentation are not supported here.
Requested seeds do not establish independently randomized sensor noise.

## Native acceptance on 2026-10-07

The final codec was executed through the normal Experiment API, durable queue
and worker on the existing Linux CARLA server. Two RGB cameras used 640×360.

| Execution | Ticks | Sensor observations | Native data bytes | Worker wall seconds |
| --- | ---: | ---: | ---: | ---: |
| 10 seconds | 100 | 400 | 188,730,933 | 7.412 |
| 30 seconds | 300 | 1,200 | 562,839,487 | 18.555 |
| Sensor A/B, 10 seconds each | 100 + 100 | 800 | 377,532,221 | 14.896 |

All four captures retained complete aligned records, zero callback drops and
confirmed cleanup/restored world settings. The A/B changed front camera FOV
from 90° to 70°. Thirty-six GPU samples had a maximum observed allocation of
4,448 MiB out of 8 GiB, including the already running CARLA server; this is a
sampled maximum, not a guaranteed peak. Worker wall time includes transport,
validation and publication. Stationary capture does not establish general
driving performance, physical sensor accuracy, p95 latency or realtime operation.

The strengthened initial-pose guard first rejected stale post-spawn readback.
Its failed job and original remote failure/cleanup manifest remain preserved;
they were not converted into a successful result. Native codec SHA-256:
`65bfab6650fe6cb5abb6c3a26843656ad5e388b763de9fc9af4d8a9d7f49b673`.

The executable acceptance entry point is `scripts/accept_four_module_sensor.py`.
It requires explicit `--live` and a fresh isolated `--state`; transport comes
from operator `AXIOM_CARLA_CAPTURE_SSH`, `_PYTHON`, `_SCRIPT` and `_DIR` settings.
It never overwrites an existing acceptance database. Original receipts/files:
`.runtime/four-module-expansion-20261007/product-sensor-v3`.

## CameraE2E bridge

**Retained RAW / ISP comparison** uses the optional
`camera-e2e-retained-isp` handler and explicitly configured loopback
`AXIOM_CAMERA_E2E_URL`. The external versioned plan fixes the original RAW,
selected array, ISP definitions, candidates and environment. Both submission
and the full returned source/stage/candidate closure are verified. Native
content-addressed aliases retain their distinct roles without duplicating
identical bytes. Redirects and incomplete exports are rejected.

The accepted software execution used two actual ISP candidates on four frames,
preserved the original RAW hash, and retained 60 native files including the full
external export and execution ID. The source is **RAW generated by an authored
synthetic sensor model**, not a measured camera capture. The same external
execution was explicitly reused by its idempotent frozen plan in the second
product acceptance; it was not counted as a second independent physical trial.
Original receipts: `.runtime/four-module-expansion-20261007/product-camera-v2`.

CameraE2E lens/sensor A/B remains unsupported by this bridge. Its current
external endpoint has no pre-execution frozen plan, and native pixel grids and
distortion are unmatched. A versioned scene/optics/sensor plan, correspondence
contract and actual end-to-end acceptance are required before enabling it.
Neither ISP comparison nor sensor capture is a quality/safety pass: typed
Verification Plans retain them as context-only evidence.
