# CARLA 제동 응답 식별과 제어기 개선 실험 제안

작성·상태 갱신: 2026-09-14. **아래 원래12개 screening 제안 중 초기화 비교4개를 명시적인 standalone protocol2로 수행했다. Brake pulse8개는 아직 실행하지 않았다.** 기존 `proportional-control/2`, emergency/unknown/hold의 brake1 동작, 시험 판정 기준과 원본 결과를 변경하지 않는다. 아래 close-lead 분석과80구간 표는 원래 실행의 역사적 근거로 유지한다.

현재 필요한 것은 제어기 상수 조정에 앞선 **명령 brake와 차량 응답 사이의 모델 식별**이다. 최신 close-lead에서는 완만한 정지 계획이 실제로 실행됐지만, brake를 줄이는 저속 구간에서 감속이 크게 증가했다. 단일 상수 `B=8m/s²`로 응답을 설명하거나 이번 한 궤적에 역으로 맞춘 상수를 검증된 모델로 제공할 근거가 없다.

## 초기화 비교의 실제 수행 범위

개발자용 [standalone 진단 도구](carla-brake-diagnostic.md)에서 injection1→throttle1→injection2→throttle2를 실행했다. 플랫폼 job/API/Run 기능이 아니며, 단일 Tesla·collision observer, LiDAR/선행차 없음, 동일한 자동 forward gear1 요청·brake0의 rest/release가 명시된 실험 조건이다. 이 조건을 기존 production 초기화의 byte 동일 재현으로 취급하지 않는다. [현재 상태](status.md) · [실제 근거](validation/carla-brake-initialization-2026-09-14.json).

네 건 모두 rest26tick 후 엄격한 안정 조건을 만족하고,4초·80개 coast 명령/81관측을 수집한 뒤 cleanup을 확인했다. Injection의 진행 방향 속도는1.957952→1.925977m/s, throttle은1.948817→0.368334m/s였다. 각 방식의 두 반복은 이 수치를 재현했지만 무작위 독립성을 입증하지 않는다.80개 명령과 다음 frame의 float32 readback은 모두 throttle/brake/steer0이며, throttle 계측 첫 관측의0.007853 throttle은 준비 마지막 명령의 readback으로 따로 남는다.

Throttle 준비 마지막5표본은1.9–2.1m/s 안에서도 계속 감속 중이었다. 이 조건은 정상상태나 초기 가속도0를 뜻하지 않는다. 계측 시작 위치가 injection보다1.142824m 앞이고 자세·준비 이력도 다르다. 원본 reported gear는 injection0/throttle1, RPM도 다르지만 구동계·타이어 힘의 원인을 확정하거나 native telemetry 단위를 보정한 것은 아니다. Injection 첫 snapshot 가속도에는 직전 속도 주입 구간이 포함된다. 이 준비 경계와 이후80개 coast 응답, 기존 첫 가속도0 지표를 각각 구분한다.

앞선 protocol1은 rest의 수직 낙하속도−3.43m/s가 공통 XYZ 속도 상한을 넘어서 초기화·계측0건으로 실패했다. 실패 원본과 당시 소스·정리 근거를 그대로 보존했다. Protocol2는 rest/목록 갱신에만 명시적인 낙하 중단 경계를 적용하며 rest 안정 조건·준비·계측의 제한은 바꾸지 않았다. 새 runner는 protocol1 실행을 거절하고 분석기는 과거 입력을 그대로 읽는다.

**Pulse8건은 미실행으로 유지한다.** Throttle coast의0.25초(step5) 속도1.754365m/s가 기존 pulse 진입 창1.9–2.1m/s를 벗어나므로, 새 초기·진입 상태 계약을 정하기 전에는 이 계획을 그대로 실행하지 않는다. 원래12개 제안 전체 완료, 제동 응답 모델 식별·보정, controller 개선 또는 주행 품질 gate 통과를 주장하지 않는다.

## 근거와 계산 범위

대상은 CARLA adapter0.8.0, server/client build1ae5356, `Town10HD_Opt`, 실제 실행 `run_1006c7a99c7346b0ac4d31840179d765`이다. 원본 폴더는 `.runtime/configurable-sensors-2026-09-14/close-lead/`다. **80명령·81개의 원본 physics/vehicle-response 관측 전체**를 사용했다. 순항1, controlled_stop42, hold37이며 실패·정지 구간도 제외하지 않았다. 앞선 전체점 변환·출력 재계산은 [0.8 인수 기록](validation/carla-configurable-sensors-2026-09-14.json)과 로컬 `configured-recompute.json`에 있다.

이번 문서의 `v∥`와 `a∥`는 원본 CARLA left-handed world 벡터를 각 관측의 수평 heading에 투영한 값이다.

```text
h_k = (cos(yaw_k), sin(yaw_k), 0)
v∥_k = velocity_k · h_k
a∥_(k+1) = snapshot_acceleration_(k+1) · h_(k+1)
Δv∥/Δt = (v∥_(k+1) - v∥_k) / (source_time_(k+1) - source_time_k)
```

명령 tick k의 ACK 뒤 frame k+1의 응답을 연결한다. 80개 ACK의 actor ID, frame/time 연속성과 reported-control RPC의 양끝 frame을 확인했다. 요청 brake를 float32로 변환하면 다음 frame의 reported brake와 **80/80 정확히 같다**. 원래 float64 요청과의 최대 차이는1.4294×10⁻⁸이다. 이는 캐시된 제어 상태 확인이며 제동 토크·힘 측정이 아니다.

원본 snapshot `a∥`와 위 속도 차분의 최대 차이는1.05435×10⁻⁶m/s²다. 같은 시뮬레이터 상태에서 나온 두 표현의 정합성이지 독립 센서 두 개의 검증이 아니다. `v∥`와 기존 XYZ speed norm의 최대 차이는0.000237512m/s다. 작은 후진 성분은 norm에서는 양수가 되므로, 정지 근처에서도 부호를 보존한다. 기존 판정의 감속·jerk는 기존 speed norm, 고정0.05s, 첫 가속도0 정의를 그대로 유지한다.

계획 순간 가속도를 다음 구간의 평균 가속도와 혼동하지 않기 위해, 부록에는 저장된 S-curve를 구간 끝까지 적분한 `a_plan_interval=(v_plan(t+Δt)-v_plan(t))/Δt`도 표시했다. 순항·hold의 해당 칸은 저장 목표 가속도0이며 별도 차량 응답 예측을 의미하지 않는다.

## 단일 폐루프 시험으로 식별할 수 없는 것

1. **명령 지연과 응답 시정수.** brake가 속도오차에 따라 계속 바뀌고20Hz로 관측됐으므로 지연, 필터, 바퀴 이력, 상태 의존 gain이 서로 섞인다. ACK는 명령 수신 경계이지 힘이 발생한 시각이 아니다.
2. **초기화 영향.** rest 뒤 `set_target_velocity`로 body 속도를 주입한 요청이 있다. 이 호출의 ACK는unknown이며 바퀴·기어·body가 같은 정상 주행 상태로 수렴했음을 증명하지 않는다. 요청2m/s와 실제 첫1.958m/s도 분리한다.
3. **속도별·이력별 brake 응답.** 이번에는 brake 상승 때 높은 속도, brake 하강 때 낮은 속도만 관측됐다. 같은 속도·같은 brake를 다른 이력에서 적용한 독립 표본이 없다. 정지마찰 전환, wheel 상태, 접촉 solver, drivetrain 등은 후보 원인일 뿐이다.
4. **평지·타이어·차량 모델의 유효 범위.** 한 map 구간·한 차량·한 설정을 경사/노면/차종으로 일반화할 수 없다. native telemetry 값을 실측 힘이나 물리 calibration으로 간주하지 않는다.
5. **초기 관측 horizon 문제와 plant 문제의 분리.** cruise의6→5→4m grid 변화에 따른 emergency latch와, 이번 close-lead의 controlled-stop 응답 불일치는 서로 다른 관측이다. 어느 하나의 상수 변경으로 양쪽을 해결했다고 할 수 없다.
6. **확률적 재현성.** 같은 요청 seed는 provenance일 뿐 현재 binary의 센서 RNG 재설정이나 반복의 통계적 독립성을 보증하지 않는다. 반복 횟수를 독립 stochastic trial 수로 바꾸지 않는다.

새 plant 모델은 우선 `Δv∥=F(v∥, 현재/최근 brake, throttle, 초기화 방식, 관측 가능한 wheel/gear 상태, 고정 physics/도로 조건)` 형태의 제한된 입력–출력 관계로 다룬다. 반응이 상태·이력에 의존하면 단일 gain 대신 구간별 응답과 지연/불확도 범위를 보존한다. 현재 결과에서 특정 고차 모델·lookup table·ABS 개선을 즉시 선택하지 않는다.

## 독립 제동 실험 protocol 제안

### 1. 실험 경계와 기록

Production perception/policy가 brake를 바꾸지 않는 **별도 plant diagnostic**으로 고정 입력을 준다. 플랫폼의 guard나 기존 판정은 바꾸지 않는다. 각 실험은 고유 ID·한 번의 제출과 원본 source hash를 가지며, 응답 유실이면 그 ID만 조사한다. 기존 runtime의 exclusive ownership, actor identity/episode 검증, sensor callback drain, 원래 actor/settings/weather 복원 규칙을 적용한다. 다른 작업이 진행 중인 서버를 임의로 중단하지 않는다.

한 trace는 현재와 같은20Hz·80명령/81관측·4초 계측으로 제한한다. 계측 전 준비도 별도 wall/tick 상한과 전체 trace를 가진다. 준비 실패를 첫 계측점으로 숨기지 않는다. 현재 Tesla blueprint·spawn transform·physics readback·고정 map 구간·weather·0.05s 설정을 pin하고, 충돌·누락 ACK·frame gap·잘못된 소유권이면 실험 실패와 prefix를 남긴다. 4초 안에 정지하지 않으면 더 긴 측정치를 추정하지 않고 censored/not_stopped를 보고한다.

모든 frame에 world XYZ velocity/acceleration/pose, v∥, yaw/pitch/roll, 요청/ACK/reported control, raw wheel telemetry와 availability, gear/scalars, source clock을 보존한다. 설정·명령 ACK·다음 관측은 각각 저장한다. 선택형 telemetry 부재를0으로 채우지 않는다. 필요하면 LiDAR를 부착하되 plant 입력에는 쓰지 않으며 센서 포함 여부를 다른 실험 조건으로 명시한다.

### 2. 원래 첫 screening 제안: 초기화4개 수행·pulse8개 미실행

다음은 최초 제안의 조건이다. 실제 수행한4개는 위 protocol2의 조건·실패 보존 범위를 따른다. 나머지8개는 발견된 pulse 진입 속도 문제 때문에 새 계약이 필요하며, 아래 문단 자체를 실행 승인으로 취급하지 않는다.

**초기화 비교4개:** 현재 rest→body target velocity 주입 경로와, 명시적 throttle 준비 경로를 각각2회 비교한다. 두 번째 경로는 제동 실험 전용 준비 제어이며 gear/자동변속 설정, 준비 명령과 도달 조건을 새 실험 recipe로 고정한다. 한 경로가 도달 조건을 만족하지 못하면 임의로 추가 속도 주입하거나 gear를 바꾸지 않는다. 같은 시작 위치·physics, 계측 시작의 실제 v∥≈2m/s·yaw·wheel 관측 이력을 비교한다. coast brake0 trace로 초기 진동과 무제동 저항을 먼저 측정한다. 도달 허용오차·지속 길이는 첫 실행 전에 고정하며 현재 rest gate만으로 wheel/body 수렴을 선언하지 않는다.

**제동 pulse8개:** 준비 경로를 명시한 뒤 시작2m/s에서 brake `[0,0.025,0.05,0.1,0.2,0.35,0.6,1]`을 각1회 적용한다. 계측 시작0.25초 동안 brake0, 다음0.25초 동안 지정 brake, 이후3.5초 brake0의80명령 sequence를 사전 생성하고 hash를 고정한다. throttle0·steer0·handbrake false·reverse false를 유지한다. brake1 조건도 빠뜨리지 않되 정지한 표본을 moving response gain 계산에 섞지 않는다. 정지/미정지 여부와 제동 해제 뒤 응답을 모두 보존한다. 이8회는 **탐색 screening이지 식별/인수 완료가 아니다**.

이 준비/계측 구성은 인지가 보고한 gap 또는 첫 실패 프레임에 반응해 pulse를 변경하지 않는다. 요청 속도와 실제 pulse 시작 속도가 다르면 조건 미충족으로 남긴다. 시험 공간/정지 거리 경계는 최초 brake0 조건도 포함하는 계측 계획에서 정하고, 경계를 벗어나면 별도 abort 원인과 요청·응답을 보존한다.

### 3. 상태와 이력을 분리하는 후속 설계

Screening이 유효하면 같은 조건을 독립적으로 새 actor를 준비해 최소3회 반복하되, 결과를 RNG 독립성 증거로 세지 않는다. 다음 확장은 **0.25/0.5/1/2m/s × 명시적 brake levels**로 속도 의존성을 분리한다. 저속0.25/0.5/1m/s에서는 우선0.05/0.2/0.35의 고정 pulse를 사용해2m/s 결과와 연결한다. 관측되지 않은 속도/level은unknown으로 남긴다.

이력은 별도 trace에서 같은 속도 창·같은 brake level을 증가/감소 sequence로 통과하도록 설계한다. 속도가 함께 변한 단일 pulse의 상승/하강만으로 hysteresis를 식별하지 않는다. 제동 유지 길이0.1/0.25/0.5초, release 이후 구간을 분리하고 run 순서를 교차 배치한다. 필요한 구동계/초기화 변경은 한 번에 한 축만 바꾸고 별도 recipe revision을 사용한다. 동작을 바꾼 후보의 기록을 기존 데이터의 보정본으로 덮지 않는다.

입력 식별에는 기존 결과에서 역산한 `B=-a/b` 한 점을 사용하지 않는다. 특히 b≈0, standstill, 부호 반전에는 gain을 발급하지 않는다. v∥와 Δv∥, 고정 구간 response integral, onset의20Hz 해상도 구간, release tail·peak·지연, 초기/정지 상태를 함께 보고한다. 관측 시간 해상도보다 세밀한 지연을 확정하지 않는다.

### 4. 모델 선택과 제어기 수정의 진입 조건

- 원본 frame/ACK/설정/해시와 초기 조건을 먼저 인수하고, speed/phase/level별 관측 분모와 실패·미도달을 공개한다.
- coast 성분과 제동의 증분 응답, 속도/이력 의존성 및 식별 불확도를 설명할 수 있어야 한다. 측정한 유효 영역 밖은unknown으로 유지한다.
- 처음부터 제외해 둔 brake sequence와 초기 속도 조건으로 검증한다. 적합에 쓴 동일 궤적의 오차만으로 모델을 채택하지 않는다. 예측 속도·가속도·정지거리 허용오차와 보수적 범위 정책은 결과를 보기 전에 실험 recipe에 고정한다. 미정이면 모델 인수 pass를 발급하지 않는다.
- 물리 제동이 추정 정지 envelope를 지지하는지와, 원하는 comfort를 추종하는지를 별도 평가한다. 기존 전체-frame 감속6m/s²·jerk10m/s³ 판정은 그대로 유지하고 signed-heading 진단을 추가한다. 정지 직전 표본을 삭제하거나 threshold를 완화하지 않는다.
- 위 근거가 생긴 후에만 controller 새 version과 명시적인 actuator/plant 가정을 설계한다. 기존 version·기존 실패 Run을 보존하고 동일 입력 replay/고정 plant 시험/실제 live를 구분한다. horizon 부족의 emergency fallback을 완화하는 변경은 이 plant 실험의 결론이 아니다.
