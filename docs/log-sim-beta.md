# Log Sim 내부 베타

목표는 내부 엔지니어 3–5명이 대표 로그로 시작해 같은 입력의 조건을 바꿔 비교하고,
조사할 Case와 검토 이유를 남기는 것이다. 이후 자신의 지원 MCAP로 반복한다.
지도·차량 asset 확대보다 이 업무의 완주를 우선한다.

## 대표 팩으로 시작하는 안내형 업무

첫 베타는 준비된 대표 로그로 진행한다. 시작 화면의 추천 ‘차간 거리’ 팩을 선택하고
원본 확인 → 조건 저장 → 실행 → 결과 조사 → Case 검토 순서로 완료한다. ‘시작’은 입력과
업무 기록만 준비하며 실제 실행은 사용자가 별도로 누른다. 사용자 MCAP 업로드는 보조 경로로 유지한다.

업무 기록은 원본 hash, 정확한 비교 설정 개정, 배치, 조사한 Case에 연결된다. `task`가 포함된
주소와 서버 기록을 통해 다시 접속해도 같은 업무를 이어간다. 저장된 결과를 만든 설정과
새 작성안을 구분한다. 다른 조건을 실행하려면 새 업무를 시작한다.

후보가 없으면 실패로 보지 않는다. 원본 구간을 직접 선택해 Case로 저장하고 차이 없음과
제어기 한계를 기록한다. 완료 조건은 연결된 배치 완료, 결과 열람 기록, Case의 ‘검토 완료’ 저장이다.
이는 소프트웨어 업무 완료이며 안전 판정 또는 사람이 도움 없이 끝냈다는 증명은 아니다.

‘막혔어요’ 의견에는 현재 단계와 실행 참조가 연결된다. 완료 의견에서 도움 필요 여부를 별도로
기록한다. 운영자는 참가자별 진행·막힌 단계·의견을 보고 JSON/CSV로 내려받는다.
원본 파일·토큰은 의견에 자동 첨부하지 않는다. 실제 사람에게 초대나 메시지를 자동 전송하지 않는다.

새 API는 `/api/v1/log-sim/beta-tasks`, `/beta-tasks/{id}/progress`, `/beta-feedback`,
운영자 전용 `/beta-overview`이며 각 경로의 접두사는 `/api/v1/log-sim`이다.
비교 설정은 ID와 revision을 지정해 정확한 이전 개정을 읽을 수 있다. Python SDK도 같은 API를 사용한다.

## 이번 구현

- 프로젝트 Engineer의 원본 MCAP 업로드, 채널 선택, 연속 구간 점검·등록. Viewer는 읽기만 가능하다.
- 목표 속도·차간 시간·정지 여유 거리의 A/B 편집, 설정 개정 저장, 정확한 개정/hash로 배치 실행.
- 원본 객체 BEV·자차 신호와 실제 reference 제어 요청의 동기 재생. 카메라는 선택 사항이다.
- 겹치는 시간 후보를 대표 후보로 묶거나 모두 펼치기. 원본 로그·분석 구간·규칙 후보의 수를 구분한다.
- 후보를 Case 묶음으로 보존하고 태그·검토 상태·메모·원본 시점 저장, 시점 링크 복원,
  해당 Case를 만든 원래 배치 후보로 돌아가기, 결과 JSON/CSV 다운로드.
- 같은 버전 API를 사용하는 Python SDK. 업로드/점검/등록, 비교 설정, 배치 실행, 검토와 내보내기를 제공한다.
- 대표 업무 팩 6개: 정지·재출발, 앞차 감속, 차간 거리, 끼어들기, 교차로, 입력 누락 오류.

## 지원하는 입력

MCAP 파일당 최대 128 MiB. JSON 채널의 정확한 schema 이름은 `axiom.PlanningEgo.v1`와
`axiom.ObjectTracks.v1`이다. 객체는 world 좌표와 크기·속도 의미를 선언해야 한다.
선택적으로 `foxglove.CompressedImage`를 함께 지정할 수 있다. 서로 다른 형식의 ROS 메시지를
자동 변환하는 범용 importer는 아직 아니다. UI의 지원 예제를 먼저 받아 형식을 확인한다.

한 원본에서 하나의 ego 채널을 선택하고 2–512개의 연속 ego 표본을 등록한다. 객체는 각 ego 시각에
정확히 대응해야 하며 표본당 최대 128개다. 누락·비정상 시각·미지원 좌표를 임의 보간하지 않는다.
같은 원본의 중복 구간은 다시 등록하지 않고 기존 구간을 사용한다. 선택 변경 후에는 다시 점검해야 한다.
원본 hash와 표본 ordinal, 설정 개정, seed, 제어기 버전 및 실행 출력 hash를 보존한다.

새 업로드는 원본의 생성 출처를 자동 인증하지 않는다. nuScenes의 기존 로컬 비상업 연구 범위도
그대로 유지된다. 코드 라이선스와 데이터·영상·asset의 외부 사용 권한은 별도다.

## 참가자 업무

1. 프로젝트 토큰으로 Workspace settings에 로그인하고 Log Sim을 연다.
2. 추천 ‘차간 거리’ 팩으로 업무를 시작하고 원본 구간을 확인한다.
3. A/B 조건 중 하나를 바꾸고 설정을 저장한다. 분석 준비 → A/B 실행을 누른다.
4. 후보 하나를 열어 원본 객체와 제어 요청을 재생하고 Case로 저장한다. 후보가 없으면 원본 구간으로 Case를 만든다.
5. 조사 이유·태그·상태를 저장하고 새로고침한다. 시점 링크와 원래 A/B 결과 복귀를 확인한다.
6. JSON/CSV를 내려받고 완료 의견과 도움 필요 여부를 기록한다. 도중에 막히면 ‘막혔어요’를 사용한다.
7. 입력 오류 팩 또는 자신의 지원 MCAP 업로드·점검·등록으로 반복한다. 카메라가 없어도 BEV로 조사할 수 있다.

기본 배치와 단일 Case의 별도 A/B 작성 폼은 서로 다른 비교다. 저장된 배치의 설정을 확인하려면
후보 조사 화면 또는 “이 Case를 만든 A/B 결과 열기”를 사용한다. 원본 로그 수는 통계적으로
독립된 도로 사건 수를 의미하지 않으며, 후보 수 역시 실패 수나 안전 점수가 아니다.

## 준비된 별도 테스트 환경

기존 발표 서비스는 재시작하지 않았다. 이전 업로드 베타 확인 주소는 `127.0.0.1:8071`이며
해당 런타임과 비공개 자격 파일은 `.runtime/log-beta-20261011/`에 보존돼 있다.
현재 안내형 확인 환경은 아래의 `8072`다. 공유 문서에 토큰을 넣지 않는다.
프로젝트 ID와 원본 연결은 해당 디렉터리의 `prepared.json`을 참조한다.

대표 원본 5개는 이전에 완료된 native CARLA 실행의 봉인된 artifact·hash·scenario 개정을
검사한 후 MCAP로 변환했다. 새로운 CARLA 실행은 하지 않았다. 원본 600/600/480/800/700개 중
첫 512/512/480/512/512개를 명시적으로 선택했으며 총 2,528개 표본이다. 이 팩은 객체 truth를
보존한 시뮬레이션 로그이며 카메라 영상은 포함하지 않는다. 원래 실행의 전체 범위는 provenance에 남긴다.
일반 업로더는 출처를 자동 인증하지 않으므로 팩 설명과 원본 lineage를 함께 확인한다.

다섯 팩의 실제 CPU reference A/B 10개 실행이 완료됐다. 분석 구간 5개, 실패·미지원 0개,
규칙 조사 후보 55개다. 제어 요청을 실제 차량이나 로그의 다음 관측에 적용하지 않는 open loop다.
학습 모델, 물리 센서, 폐루프 차량 반응 또는 안전성 검증으로 설명하지 않는다.
입력 오류 팩은 작성한 소프트웨어 입력 예제로 구분한다.

## 재현 도구

- `e2e/fixtures/log_sim_beta_server.py RUNTIME --port 8071`: 독립 workspace와 reference 전용 worker.
  먼저 `cd frontend && npm run build`를 수행하고 저장소 루트에서 `.venv/bin/python`으로 실행한다.
- `scripts/prepare_log_sim_beta.py RUNTIME --source-workspace PATH --pack-jobs JOBS.json`:
  다섯 팩 ID에서 보존 execution ID로의 명시적 매핑을 받는다. 원본 workspace는 읽기만 하며,
  로컬 대상 API로 프로젝트·입력·팩 binding을 만든다. 기본 API는 `http://127.0.0.1:8071`이다.
- `node e2e/log-sim-beta.mjs RUNTIME`: 실제 UI 업로드부터 검토·시점 복원까지 수행한다.
  새로운 비교·Case를 생성하므로 격리된 테스트 프로젝트에서만 실행한다.
- `docs/validation/log-sim-beta-20261011.json`: 검사 범위·보존 결과와 미완료 인수 항목.

## 안내형 베타 준비와 확인 · 2026-10-11

기존 발표 서비스는 유지했고 새 안내형 베타는 별도 `127.0.0.1:8072`에서 확인했다.
`.runtime/log-guided-beta-20261011/participants.json`에 참가자 프로젝트 3개, 준비된 팩과
비공개 토큰 파일 경로를 보존했다. 각 프로젝트에는 보존 CARLA 원본 5개와 입력 오류 안내 팩이 있다.
같은 준비 명령을 다시 실행해 프로젝트·토큰·원본을 추가하지 않고 준비 상태를 확인했다.
실제 참가자에게 초대를 보내거나 공개 접속을 열지는 않았다.

```sh
.venv/bin/python e2e/fixtures/log_sim_beta_server.py RUNTIME --port 8072
.venv/bin/python scripts/prepare_log_sim_beta.py RUNTIME \
  --source-workspace SOURCE_WORKSPACE --pack-jobs PACK_JOBS.json \
  --api-url http://127.0.0.1:8072 --participants 3
.venv/bin/python e2e/fixtures/log_sim_guided_inputs.py RUNTIME
node e2e/log-sim-guided-beta.mjs RUNTIME
node e2e/log-sim-guided-recovery.mjs RUNTIME
node e2e/log-sim-guided-retained.mjs RUNTIME
```

서버 명령은 별도 터미널에서 유지한다. `PACK_JOBS.json`은 다섯 팩 ID를 기존 execution ID에
연결한 명시적 JSON이며 이번 로컬 준비 디렉터리에 보존돼 있다. 참가자 이름은
`--participant-label`을 참가자 수만큼 지정할 수 있다. 기본값은 번호가 붙은 엔지니어 이름이다.
두 실행 브라우저 검사는 격리된 테스트 프로젝트에 실제 reference 실행·Case·의견을 만든다.
마지막 retained 검사는 기존 결과만 읽는다.

API·SDK·준비 도구의 집중 검사 73개를 통과했다. 대표 팩 업무, 입력 오류 복구, 후보 없는
수동 Case, 제출 응답 유실 후 같은 배치 복구를 정상 브라우저로 확인했다.
새 reference 실행은 보존 CARLA 입력의 A/B 2개와 작성한 객체 없는 입력의 A/B 2개다.
이번 변경에서 CARLA를 새로 실행하지 않았으며, 기존 발표 서비스를 재시작하거나 공개 배포하지 않았다.
브라우저의 완료 의견은 자동 점검임을 명시해 실제 사람의 독립 완료와 구분했다.
상세 근거는 [안내형 베타 확인 기록](validation/log-sim-guided-beta-20261011.json)을 참조한다.

## 남은 베타 인수

실제 참가자 초대와 사람 3명 이상의 도움 없는 업무 완료는 아직 수행하지 않았다.
참가자별 프로젝트·최소 권한 토큰 배정, 사용 가능한 저장 용량과 운영 담당자 확인 후 진행한다.
5명 중 4명 이상이 등록→비교→Case 기록을 완료하는 것을 초기 목표로 삼는다.
범용 ROS/MCAP 변환, 더 긴 로그의 분할·대용량 처리, 지도 확장, asset 확장, learned model 연결,
closed loop와 상세 물리 상관 검증은 후속 범위다. 공개 호스팅이나 기존 서비스 반영도 별도 작업이다.
